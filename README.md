# Release A.1 — Tally trial balance and signed-PDF input

- **Three ways in:** standard template, Tally trial balance (xlsx/xls/csv), or signed/provisional statements (text PDF, both years).

# MIS Dashboard — Working Capital Redesign

## Latest change — ageing charts no longer require an MSME column

**Bug fixed:** on the Trade Payables tab, the stacked ageing charts and bucket summary tables were
nested inside the "MSME split disclosed" branch. That meant a company whose payables ageing file
had no MSME column saw **no charts at all**, even though the bucket data was perfectly good — the
charts don't need to know MSME status to draw.

Now:
- **Ageing charts always render** when ageing data exists. With an MSME column you get two charts
  (MSME risk-coded red-for-old, non-MSME value-coded green-for-old). Without one, you get a single
  combined chart, value-coded, since untagged payables are treated as ordinary trade credit.
- **Only the genuinely MSME-dependent sections stay gated**: the split day-count cards and the
  Section 43B(h) tax disallowance calculator. Those legitimately can't be computed without knowing
  which suppliers are MSME.

## Management summary — rebuilt

The Overview summary is no longer a generic paragraph. It now returns three fixed sections:

- **OVERALL** — leads with the relationship between two figures (e.g. revenue grew X% but
  receivables grew Y%), and names the business consequence in plain language
- **WHAT'S GOOD** — genuine positives only, each backed by a number
- **WHAT'S CONCERNING** — each point quantified in rupees where possible, most urgent first

Two things make this work rather than producing vague AI filler:

1. `buildVarianceContext()` in `src/lib/buildContext.ts` **pre-computes every percentage in code**
   — growth rates, margin movements in percentage points, working-capital day changes, and the
   rupee value of one day of debtor/inventory days. The model interprets these numbers; it never
   calculates them. That's what keeps the figures arithmetically correct.
2. The prompt explicitly requires a number attached to every claim, and requires explaining *why*
   a movement matters rather than just restating it.

The `StructuredSummary` React component parses the three sections and renders them with colour
coding (neutral / green / red). If the model ever returns an unexpected shape, it falls back to
showing the plain text rather than rendering nothing.

## What changed in *this* delivery (five corrections + real product additions)

Five specific corrections were made after reviewing a working prototype, verified against real
numbers before being ported into this production code (see the compute functions in
`src/lib/workingCapitalCompute.ts` for the exact formulas):

1. **Finance cost rate was wrong.** The what-if sliders' "finance cost saved" figure divided
   total interest cost by short-term borrowings only, producing an unrealistic ~30-40% implied
   interest rate. Fixed to a blended rate — total interest cost ÷ total loans (secured +
   unsecured + short-term) — giving a realistic ~12-15%.
2. **MSME payables slider removed, replaced with a real calculation.** The 45-day MSME payment
   limit is a legal ceiling, not something to "optimize" with a slider. The Trade Payables tab
   now shows which MSME suppliers are actually past 45 days and calculates the resulting income
   tax exposure under Section 43B(h) (disallowed expense × an adjustable tax rate), rather than
   a meaningless "what if we extended it" scenario.
3. **Trade Payables ageing chart colors were backwards for non-MSME suppliers.** Longer-aged
   non-MSME payables are good (more free trade credit), but the chart still colored them red
   like a risk signal. MSME and non-MSME ageing charts now use genuinely different color
   schemes — matching the (already-correct) flag logic that was fixed in an earlier delivery.
4. **New inventory scenario**: discard identified slow-moving stock (an adjustable liquidation
   recovery rate splits the value into cash recovered vs. a one-time write-off) and reinvest the
   proceeds in the fastest-turning item — with the resulting incremental revenue/profit clearly
   labeled as an assumption (uses company-wide gross margin as a stand-in, since item-level
   margins aren't available), not a guarantee.
5. **Financial Ratios tab now shows an "ideal" benchmark, direction-aware arrow, and a short
   remark for every ratio with a genuine, defensible universal target** (Current Ratio, Quick
   Ratio, Debt-to-Equity, Debt-to-EBITDA, Interest Coverage, Debtor Days, Inventory Days).
   Margins, ROCE, ROA, and turnover ratios deliberately have no invented "ideal" — they're
   sector-dependent, and the tab says so rather than making up a number.

**Real product addition that came out of building #4**: the app never had a path for item-wise
inventory data before (only receivables/payables ageing). This delivery adds it — a new
`disclosedInventoryAgeing` field, a new "inventory" sheet type in the upload parser (detects
Item/Category/SKU + Value + Days-on-Hand style columns), and full ageing chart + slow-moving
stock table rendering on the Inventory tab, matching the same pattern already used for
receivables/payables. When no item-wise file is uploaded, the tab shows a clear "not available"
note rather than the discard scenario — same honesty pattern as everywhere else in this app.

**How this was verified**: every new calculation was tested against hand-computed expected
values (not just "does it compile") using the exact same sample dataset from the approved
prototype — confirmed to the rupee. The new React components (chart, MSME tax card, inventory
discard card, ratio rows) were also rendered server-side with real *and* empty-array inputs to
catch runtime errors before delivery, since this sandbox can't run a full Next.js dev server.

## Important limitation to know about: the MSME/non-MSME payables split

Real Schedule-III-format audited statements (like the SRB or Sunex files used earlier in this
project) disclose MSME vs. non-MSME creditors as **two separate aggregate ageing tables**, not
as a column on a vendor-by-vendor list. The generic parser change in this delivery only handles
the second case — a vendor-wise ageing upload with an explicit "MSME" column. It does **not**
yet automatically extract the two-table Schedule-III disclosure format the way the earlier
company-specific dashboards (SRB, Sunex) did by hand.

In practice, this means: **most real uploads today will show "no split disclosed" and fall back
to the non-MSME rule for the whole Trade Payables figure** — which is the correct, safe default
per the spec (absence of a disclosed split isn't treated as evidence of a compliance risk), but
it does mean the compliance-specific MSME view won't show up automatically for files structured
like SRB's or Sunex's. Building a parser for that two-table Schedule-III format is a reasonable
next step if this matters for real usage — it's a bounded, well-understood addition given we've
already parsed that exact structure by hand twice in this project.
